# Hermes v4.0 Implementation Plan

**Status:** Draft
**Created:** 2025-01-21
**Total Duration:** 10 weeks (3 phases)

---

## Overview

Hermes v4.0 represents a ground-up rearchitecture of the agent runtime, moving from a monolithic execution model to a pipeline-based architecture with first-class streaming, structured output, and observability. This plan covers 27 features across three phases.

## Design Decisions

### DD-01: Pipeline over Actor Model
We chose a functional pipeline (`Prompt → Stream → Tools → Output`) over an actor-based system. Rationale: pipelines are easier to trace, test in isolation, and reason about for a team of 4–6 engineers. Actors remain a future consideration for true concurrent multi-agent loops.

### DD-02: Streaming as First-Class, Not Optional
All features must work in streaming mode. Batch/non-streaming is implemented as "collect all events then return," not as a separate code path. This prevents feature divergence.

### DD-03: Constrained Decoding Over Post-Hoc Validation
We prioritize constrained decoding (grammar-based) with post-hoc JSON repair as a fallback. Relying solely on prompting or post-hoc validation has shown >2% failure rates in benchmarks; constrained decoding drops this below 0.1%.

### DD-04: OpenTelemetry over Proprietary Tracing
Standardizing on OTel from day one avoids vendor lock-in and gives us free integrations with Grafana, Datadog, and Jaeger. The cost is a heavier dependency, but it's justified for a production system.

### DD-05: Tool Schema = JSON Schema 2020-12
Tool definitions use JSON Schema 2020-12 exclusively. No custom DSL. This maximizes interoperability with existing ecosystems (FastAPI, Pydantic, TypeBox, Zod).

## Risks

| ID | Risk | Likelihood | Impact | Mitigation |
|----|------|------------|--------|------------|
| R01 | Constrained decoding not supported by all providers (e.g., Anthropic) | Medium | High | Implement provider abstraction; fall back to post-hoc repair for unsupported providers |
| R02 | Streaming backpressure causes head-of-line blocking | Medium | Medium | Use bounded buffers with explicit overflow policy; benchmark with 10k concurrent streams |
| R03 | Multi-agent delegation creates unbounded cost loops | High | High | Hard delegation depth limit (default 5), per-run token budget, circuit breaker on total spend |
| R04 | OTel instrumentation adds >10ms latency per span | Low | Medium | Profile early in Phase 2; use sampling (default 10%) for high-throughput paths |
| R05 | Phase 1 slips into Phase 2 timeline | Medium | Medium | F01–F04 are hard-gated; if not complete by end of Week 2, cut F08 and F11 from Phase 1 |
| R06 | Provider API breaking changes during development | Medium | Low | Pin provider SDK versions; abstract behind provider interface; allocate 1 day/week for upstream tracking |

## Success Criteria

### Quantitative

| Metric | Target | Measurement |
|--------|--------|-------------|
| End-to-end streaming latency (first token) | < 200ms p95 | Synthetic benchmark, 1000 runs |
| Structured output schema compliance | > 99.9% | 10k-run test suite with 5 schema complexities |
| Trace completeness | 100% of runs have a trace | CI assertion on trace export |
| Concurrent stream capacity | 10,000 simultaneous | Load test with k6/Gatling |
| Delegation cycle detection | 0 false negatives | Property-based tests with arbitrary delegation graphs |
| Pipeline stage test coverage | > 90% | `cargo test --coverage` / `vitest --coverage` |

### Qualitative

- [ ] A new engineer can add a tool and see it streamed in < 30 minutes (documented walkthrough exists).
- [ ] A production incident can be diagnosed entirely from exported traces without log diving.
- [ ] Switching LLM providers requires changing only configuration, not code.
- [ ] The system degrades to a fallback model without dropping in-flight streams.
